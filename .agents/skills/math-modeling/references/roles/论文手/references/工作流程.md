# 论文手工作流程

## 一、锁定官方规则

生成前确认目标竞赛、届次、语言和官方规则来源。优先使用用户提供或从官方网站取得的当届官方 Word 模板、摘要页、编号页和格式说明。把规则来源与届次记录在内部检查中，不把往届经验写成固定规则。

## 二、检查输入

必须具备：

- 题目及附件
- `题目分析报告.md`
- `术语表格.md`
- 可运行代码
- 实际运行结果表格
- 原始数据图、模型运行过程图和最终结果图
- 已核验的文献元数据

关键输入缺失时回退到对应角色补齐，不能推测数值、伪造图表或编造引用。

## 三、内部论证映射

写作前在内存或临时工作区建立主张—证据映射：每个结论对应公式、表格、图、代码输出或文献。映射只用于检查，不作为额外交付物。

同时记录两类篇幅约束：一类是当届官方页数、摘要和文件限制，必须满足；另一类是论文完整度质量目标，可以由用户覆盖。CUMCM未给出更具体要求时，摘要按渲染后的有效区域充实度调整，不使用固定字数；正文以渲染后恰好30页为优选目标，但不得靠重复、空泛文字、放大图表、段前分页或制造空白凑页。一级标题默认连续排版，只在摘要到正文、正文到附录等结构边界或确有避免孤行、拆表等需要时分页。以2026年官方规范为例，30页上限只适用于正文；附录页数不限，电子版论文只受20MB文件大小限制，不得用PDF总页数代替正文页数检查。

不要把优秀案例中代码页占比约20%等观察值转化为硬约束。代码附录的首要要求是全部、完整、可运行并与支撑材料一致；可在不删减必要源码的前提下改善字号、行距、折行和空行，但不得为了压低占比而省略程序。

规划图形时同时考虑“结果证据图”和“方法解释图”。前者从真实运行数据生成；后者可用 Python、矢量绘图或流程图工具生成算法流程、模块关系、几何构造与验证闭环。每幅图都必须在正文被引用并承担具体信息功能，解释图不得伪造数值、误导比例或替代必要的结果证据。

## 四、构建 DOCX

1. 从当届官方参考模板创建文档；模板正文示例必须清除，但保留样式、分节、页眉页脚和页面设置。
2. 使用 `../../../../tools/docx/scripts/paper_format.py` 添加标题、段落、公式、表和图片。
3. LaTeX 只作为公式输入，转换成 Word 原生 OMML；不支持的命令必须报错。
4. 表格使用可编辑 Word 表格；图使用编程手实际生成的文件。
5. 每幅图和每个表均设置连续编号与题注，并在正文中至少引用一次；文献编号、正文引用和 DOI 双向核对。

## 五、验证

```powershell
python ../../../../tools/docx/scripts/self_check.py
python ../../../../tools/docx/scripts/office/validate.py "<PROJECT_ROOT>/完整论文.docx"
```

另需调用 `paper_format.validate_paper_structure()` 检查篇幅、公式/图/表数量、图表正文引用与参考文献对应关系；分别传入PDF总页数 `rendered_pages`、正文页数 `rendered_body_pages`、摘要页有效区域填充率 `abstract_fill_ratio` 和电子论文文件字节数 `electronic_file_size_bytes`。30页硬约束只检查 `rendered_body_pages`，20MB硬约束只检查电子文件大小；摘要质量按最终渲染填充率判断。随后抽检分页、公式、图表、页眉页脚和目录。任何错误或无合理覆盖依据的预警都应修复后重新生成。

## 六、交付

只交付 `PROJECT_ROOT/完整论文.docx`。临时 Markdown、内部映射、检查日志和中间 DOCX 不作为交付物。
