# 红队评审门与证据等级

本参考用于完整建模交付、赛后审稿和依据评审意见修改论文。评审手先证明“算的对象正确”，再评价“算得是否够好”。

- 必查维度

## 必查维度

| 检查键 | 检查内容 | 常见反例或证据 |
|---|---|---|
| `data_integrity_and_leakage` | 数据血缘、行列完整性、去重/缺失处理以及训练—调参—最终验证隔离 | 首行误作表头、重复样本跨集合、未来或同组信息泄漏 |
| `domain_and_visibility` | 样本域、可见域、评价对象是否正确 | 内部点误入轮廓、不可达状态、评价域错位 |
| `boundary_and_extremes` | 边界、极端值、零输入和终止事件 | 无资源、寿命结束、上下界、空集合 |
| `units_and_invariants` | 量纲、守恒、单调性和不变量 | 严格模型不得优于放松模型、概率和为1 |
| `parameter_semantics_and_constraints` | 核心参数的定义、单位、允许域、全域行为、可辨识性及约束对照 | 参数越界/贴边、反常符号、跨数据漂移、参数补偿、拟合改善掩盖非法参数 |
| `objective_metric_alignment` | 优化目标、训练损失、模型选择指标和题目最终评价口径是否一致 | 用训练残差替代决策损失、代理目标改善但题目指标恶化 |
| `validation_and_uncertainty` | 数据切分、样本外验证、误差传播、区间覆盖和结论稳健性 | 只报拟合内误差、置信区间未校准、忽略输入误差 |
| `implementation_and_oracle` | 代码是否由有区分力的解析极限、手算小例、枚举/精确解、独立实现、不变量或变形关系核验 | 程序能运行却索引错位、输入参数未生效、演示硬编码替代计算、启发式无小规模真值 |
| `set_and_time_measure` | 并集、交集、重叠和时间窗口 | 独立时长和不得代替联合并集 |
| `marginal_contribution` | 统一目标方向后的多资源独立效果、联合效果与删除损失 | 最小化目标沿用最大化符号；删除资源后目标不变却声称有贡献 |
| `discrete_assignment` | 离散空间、候选生成与同预算复算 | 启发式固定指派包装成全局最优 |
| `stochastic_stability` | 多随机种子、初值和超参数 | 单一种子偶然最优、收敛曲线误读 |
| `grid_convergence` | 时间、空间、网格或采样加密 | 末级仍漂移却保留过多小数 |
| `cross_output_consistency` | 摘要、正文、表、图、附录同源 | 同一指标在两张表中不同 |

每项必须是：

- `pass`：已执行且有证据文件；
- `fail`：发现错误；
- `pending`：尚未验证；
- `na`：确实不适用，并写明理由。

完整建模发布中，`data_integrity_and_leakage`、`objective_metric_alignment`、`implementation_and_oracle` 和 `cross_output_consistency` 始终适用，不得标为 `na`。没有经验数据时，数据完整性仍须覆盖题目输入、常量、附件和合成测试数据的来源与形状；没有可用 oracle 时应保持 `pending` 并阻断发布，而不是把未验证写成不适用。

### 实现 oracle 的最低要求

`implementation_and_oracle` 不能只证明“代码能运行”或“输出看起来合理”。至少登记一个能让常见错误实现与正确实现产生不同结果的 oracle；对各核心例程优先组合以下方法：

- 手算或解析小例，覆盖方向、单位、边界和退化情形；
- 小规模枚举、成熟精确求解器或与主实现不同技术栈的独立实现；
- 守恒、单调、对称、置换不变、缩放关系等不变量或变形测试；
- 故意构造会暴露未使用参数、固定演示答案、索引错位、训练/测试泄漏和错误目标方向的区分性反例。

同一代码路径生成的第二份文件、同一错误公式的重写、只在“顺手样例”上相等以及把待审实现自身当作期望值，都不构成独立 oracle。每个 oracle 记录 `id`、`type`、`target`、`discriminating_case`、`expected`、`observed`、`status` 和证据文件；`oracle_audit.coverage_statement` 说明覆盖了哪些核心例程及尚未覆盖的范围。

## 主张证据等级

| `strength` | 允许措辞 | 最低证据 |
|---|---|---|
| `feasible` | 可行方案 | 全部硬约束和核心判据通过 |
| `budget_best` | 当前搜索预算或已比较候选中的较优方案 | 公开搜索空间、预算、多种子或候选对照 |
| `discrete_global` | 离散层全局最优候选 | 穷举或可验证地覆盖全部离散组合；连续层单独降级 |
| `global` | 全局最优 | 严格证明或具有可核验全局保证的算法与条件 |

论文手不得提高审计文件给出的等级。“收敛曲线变平”“局部扰动没有更优点”只支持局部稳定或当前预算较优，不支持全局最优。

## 多资源删除试验

对资源集合 `S`，先明确无资源基线并把评价量统一成“越大越好”的效用 `U`。若原问题最大化 `J`，可取 `U=J`；若原问题最小化 `J`，可取 `U=-J`，或直接使用下式给出的等价成本差。不同量纲或多目标结果不能在没有预先声明标度与偏好的情况下任意加权。

```text
独立效果_i = U({i}) - U(∅)
联合效果 = U(S) - U(∅)
删除损失_i = U(S) - U(S\{i})

若 J 越小越好：删除损失_i = J(S\{i}) - J(S)
```

- 删除损失为正：可声称该资源对当前集合有正边际贡献。
- 删除损失为零：只能写冗余、备用或当前方案中无边际贡献。
- 删除损失为负：该资源在当前评价和重优化口径下可能有不利作用，也可能暴露非单调交互、成本漏计或实现错误；必须复核，不能自动改写为正贡献。
- 每次删除后应在相同约束、预算和求解精度下重新优化；若删除使问题不可行，单独报告“维持可行性的关键资源”，不得用随意选取的罚值或无穷大伪装成可比边际数值。

## 离散—连续耦合

1. 明确离散组合总数和覆盖约束。
2. 用低预算或上界筛选候选，但保留筛选方法和随机种子。
3. 对入围候选使用相同连续优化预算复算。
4. 报告实际比较集合、未覆盖范围和推翻条件。
5. 只有全部离散组合都被可验证覆盖时，才允许使用 `discrete_global`。

## 结果注册表

`result_registry.json` 为论文重复数值的唯一来源。每条至少包含：

```json
{
  "key": "problem3.union_duration_s",
  "value": 4.655,
  "unit": "s",
  "precision": 3,
  "source": "results/结果摘要.json",
  "generated_by": "python 求解.py --seed 42"
}
```

同一 `key` 不得重复；论文构建脚本只读取注册表，不再次手写数值。

评审阶段运行 `result_registry_gate.py`。旧字段 `generator` 必须迁移为 `generated_by`，旧顶层容器 `values` 必须迁移为 `entries` 或稳定键映射；`precision` 统一表示非负整数小数位数，无量纲量的 `unit` 写 `1`。`value` 不得为 NaN 或无穷大。`source` 必须指向 `PROJECT_ROOT` 内实际存在的数据、配置、图片或运行日志，可在路径后的 `:` 或 `#` 添加表名、字段或定位说明；代码文件不作为数值来源，执行入口写入 `generated_by`。

## 参数审计

完整规则见 `参数语义与约束审计.md`。`parameter_audit` 必须覆盖所有影响核心结论的拟合参数、决策变量、阈值、锚点和数值松弛量，而不是任选一个示例参数。每项至少记录语义与角色、单位、允许域及依据、观测值/范围、全研究域行为、状态和证据。

参数越界、贴边、反常、跨数据漂移、强耦合或跨模型冲突时，将 `boundary_risk` 设为 `true`，并提供同数据同预算的 `constraint_refit`。若任务确实没有任何需要估计、优化、校准或人为设定且影响结论的参数，才可把整个参数审计标为 `na` 并解释。

## 通过条件

- 十四项检查均为 `pass` 或有理由的 `na`，其中四个始终适用项必须为 `pass`。
- `implementation_and_oracle` 含非空覆盖声明和至少一个状态为 `pass` 的区分性 oracle；oracle 不能与待审实现共享同一错误来源。
- `parameter_audit` 覆盖完整；边界风险含约束重拟合；参数或跨模型冲突不存在未解决的 `fail/pending`。
- 所有关键主张状态为 `pass`，证据和推翻条件非空。
- `critical`、`major` 发现均已关闭；`pending` 不得被包装成通过。
- 每条 `finding` 的 `severity` 只能为 `critical`、`major` 或 `minor`，`status` 只能为 `open` 或 `closed`；关闭的关键发现必须记录 `resolution` 与修复证据文件。
- `global` 主张必须具有非空的严格证明说明。
- 论文中的主张强度不高于审计等级。

正式运行 `red_team_gate.py` 时，所有 `evidence` 必须引用 `PROJECT_ROOT` 内实际存在的文件，不能只写描述性文字或不存在的占位路径。`--schema-only` 只用于测试夹具与模板开发，不能作为论文发布依据。
